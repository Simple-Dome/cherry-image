# Image 三域名发布矩阵

Image 使用单一 `main` 集成线。`gptch.cloud`、`artworkers.online` 和
`aiunify.xyz` 不是三个长期分叉的生产分支，而是三个独立的 release
profile：每个 profile 都有自己的 parent/Canvas source pair、不可变 release
ref、detached worktree、构建参数、镜像证据、上传 edge 和 MinIO 边界。

```text
main@<parent-sha>
  |-- gptch.cloud       -> refs/image-release/gptch.cloud/<task>/<parent-sha>
  |-- artworkers.online -> refs/image-release/artworkers.online/<task>/<parent-sha>
  `-- aiunify.xyz       -> refs/image-release/aiunify.xyz/<task>/<parent-sha>
```

## 本地准备

控制端必须使用干净的 attached checkout，且 parent SHA 已推送并包含于
`origin/main`。一次矩阵准备只创建本地 source evidence，不构建镜像、不传输
归档、不加载 Docker、不启动候选、不切换 Nginx：

```bash
git submodule update --init --recursive
SOURCE_REF="$(git rev-parse HEAD)"

scripts/deploy/release-control.sh prepare-matrix \
  --task-prefix image-release-20260819 \
  --source-ref "$SOURCE_REF" \
  --domains gptch.cloud,artworkers.online,aiunify.xyz
```

命令会为每个域名创建：

- `refs/image-release/<domain>/<task-id>/<parent-sha>` 不可变 source provenance ref；
- 一个干净的 detached worktree；
- `.agents/state/tasks/<task-id>/process.md` manifest；
- 后续可独立生成的 composite source archive。

每一行的 manifest 会记录域名、parent SHA、Canvas gitlink、Shell/Canvas
Dockerfile SHA、构建参数和允许路径。域名之间不能复用 worktree、archive、
镜像、Nginx snippet、容器、volume、Bucket、凭据或 MinIO 对象命名空间。

## 域名构建输入

Shell 每个 profile 使用 `VITE_BASE=/image/` 和对应的
`VITE_FIXED_API_BASE_URL=https://<domain>`。Canvas 使用
`VITE_BASE=/canvas/` 和相同的 `VITE_FIXED_API_BASE_URL`。

Canvas source 只保留参数化输入：

```ts
export const FIXED_API_BASE_URL = (import.meta.env.VITE_FIXED_API_BASE_URL || "").trim().replace(/\/+$/, "");
```

因此同一个 parent SHA 可以产生三个不同的域名镜像，但每个镜像的构建和
运行证据仍然必须独立记录。`/canvas/` 的静态资源、站内导航和刷新也必须
保持此前缀。

## 发布边界

矩阵准备不是生产授权，也不代表 profile 已经 ready。每个域名仍必须单独
完成新鲜 topology discovery、Shell/Canvas/uploads edge Blue/Green 候选、
`linux/amd64` 构建验证、锁、明确的生产授权、Nginx 原子事务、公共路由和
浏览器验收。普通 Image 发布只处理所选 profile 的 `/image/`、`/canvas/`
和 `/canvas-uploads/`，不触碰根路径、New API、数据库、Redis 或 MinIO
持久数据迁移。

## 远端传输与上传验收

生产归档传输使用仓库内的 `scripts/deploy/remote-release-helper.sh`。每个
数据块都通过独立的 Base64 数据 SSH 发送；控制 SSH 使用 `ssh -n`，不会读取
下一个数据块的 stdin。目标端先写入 `.partial`，逐块检查字节数和 SHA-256，
全部拼接后再检查完整归档 SHA-256，最后才原子改名。发现任意 `.partial` 时
会 fail-closed，不会继续 `docker load`。

```bash
scripts/deploy/remote-release-helper.sh transfer-archive \
  --remote newapi-16 \
  --remote-dir /root/image-release/<task>/incoming \
  --archive .release-artifacts/<task>/shell.image.tar
```

需要执行远端事务时，先把脚本作为受校验的临时文件传输，再由同一个 helper
执行；不要把长 heredoc 嵌套在承载归档数据的 SSH 管道中：

```bash
scripts/deploy/remote-release-helper.sh run-transaction \
  --remote root@155.103.156.90 \
  --script /tmp/gptch-cutover.sh \
  --remote-script /root/image-release/<task>/gptch-cutover.sh
```

uploads edge 的专用探针使用 `scripts/deploy/uploads-probe.sh`，调用方必须显式
传入对应域名、颜色和临时对象的 signed PUT/GET/DELETE URL。探针只执行
`PUT -> GET -> SHA-256 -> DELETE -> GET 404`，不发现凭据、不修改 MinIO 配置；
任一步失败都会尝试删除已写入的临时对象。

## 阶段与线上拓扑

每个 release task 的 `process.md` 都包含 `Release State`。它只允许从 source
preparation 依次推进到 composite、local verification、live discovery、构建、
候选、切流、公共验收和 closed；状态为 `blocked` 时，后续转换会 fail-closed。
`scripts/deploy/release-control.sh` 当前只推进 source、composite、local verification
及记录 fresh topology 后的 live discovery 阶段；任何构建、候选或生产阶段仍需单独
的授权流程和对应证据。

`Profile` 里的 `Documented Status` 只描述静态资料，不表示线上实际可发布。新的
selected-domain discovery 应保存为只包含拓扑结论的本地 evidence 文件：域名、UTC
观测时间、Shell/Canvas/uploads 的 Blue/Green 检查和 MinIO 隔离检查。控制器记录
该文件的 SHA-256 后，使用以下命令记录、查看和放行检查：

```bash
scripts/deploy/release-control.sh record-live-topology \
  --task-id <task> --domain gptch.cloud --evidence-file <topology.env>

scripts/deploy/release-control.sh live-status \
  --task-id <task> --domain gptch.cloud

scripts/deploy/release-control.sh assert-live-ready \
  --task-id <task> --domain gptch.cloud --max-age-seconds 1800
```

`assert-live-ready` 只有在 evidence 对应 selected domain、四项检查均为 `ready`、
SHA-256 有效且观测时间未过期时才通过。它不构建镜像、不连接生产，也不会用静态
Profile 覆盖 live 结论。

`<topology.env>` 必须恰好包含一项 `domain`、`observed_at`、
`shell_bluegreen`、`canvas_bluegreen`、`uploads_bluegreen` 和
`minio_isolation`。四个检查使用 `ready`、`not-ready` 或 `unknown`；只有全为
`ready` 才会记录 `live_status=ready-for-bluegreen`。
